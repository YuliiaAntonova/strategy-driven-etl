# solid_etl_refactor_template

A refactoring template for an ETL + AI indexing project.

## What this project does

This project separates concerns into two layers:

1. **Data platform layer**
   - ingestion
   - normalization
   - hash-based change detection
   - historized writes into Postgres

2. **AI application layer**
   - build AI-ready documents from current records
   - chunk long content
   - create embeddings through pluggable embedders
   - persist AI artifacts
   - retrieve relevant chunks
   - answer questions through pluggable LLM providers

The architecture is profile-driven and registry-based. The orchestration layer depends on contracts, not on concrete implementations.

## Architecture principles

- **Single Responsibility**: extractor, transformer, detector, writer, chunker, retriever, provider all do one job
- **Open/Closed**: new detectors, writers, chunkers, retrievers, or providers are added through registries
- **Liskov Substitution**: pipeline and AI flows work with contracts
- **Interface Segregation**: ETL contracts and AI contracts are separated
- **Dependency Inversion**: use cases depend on registries and interfaces, not on raw SQL or provider-specific calls

## Data layer

### ETL profiles

- `full_refresh`
  - detector: `full`
  - initial writer: `replace`
  - later chunk writer: `append`
- `historized_snapshot`
  - detector: `incremental-by-primary-key-and-hash`
  - writer: `versioned`

### System column logic

- `date_created` — when the entity first appeared
- `date_loaded` — when the current version was loaded
- `row_hash` — calculated only from business columns in `HASH_COLUMNS`
- `is_current` — current active version of the entity

### Versioned behavior

- new `primary_key` → insert current row
- same `primary_key` + same `row_hash` → do nothing
- same `primary_key` + changed `row_hash`:
  - old row becomes `is_current = false`
  - new row is inserted with `is_current = true`
  - old `date_created` is preserved
  - new `date_loaded` is generated by the pipeline

## AI layer

### AI profile

- `jobs_rag_local`
  - chunker: `recursive`
  - embedder: `token_frequency`
  - retriever: `keyword`
  - llm provider: `template`

This default profile works locally and does not require external model APIs. You can add production providers later through the same contracts and registries.

### AI flow

1. read current jobs from Postgres (`is_current = true`)
2. build AI documents
3. chunk documents
4. create embeddings
5. write AI documents and chunks into Postgres
6. answer questions by retrieving relevant chunks and calling the configured LLM provider

## Commands

### 1. Ingestion → local CSV

```bash
python3 -m src.entrypoints.cli run-jobs-ingestion
```

### 2. Full refresh (recommended for first load)

```bash
python3 -m src.entrypoints.cli run-etl --profile full_refresh
```

Equivalent explicit command:

```bash
python3 -m src.entrypoints.cli run-etl   --load-mode full
```

### 3. Full refresh with chunks

```bash
python3 -m src.entrypoints.cli run-etl   --profile full_refresh   --extract-chunk-size 10000   --write-chunk-size 5000
```

Behavior:
- first batch uses `replace`
- following batches append into the rebuilt table

### 4. Historized snapshot (recommended incremental mode)

```bash
python3 -m src.entrypoints.cli run-etl   --profile historized_snapshot   --primary-key id
```

Equivalent explicit command:

```bash
python3 -m src.entrypoints.cli run-etl   --load-mode incremental-by-primary-key-and-hash   --primary-key id   --hash-column row_hash
```

### 5. Historized snapshot with chunks

```bash
python3 -m src.entrypoints.cli run-etl   --profile historized_snapshot   --primary-key id   --extract-chunk-size 10000   --write-chunk-size 5000
```

### 6. Other detector modes through the same versioned write semantics

#### Incremental by date

```bash
python3 -m src.entrypoints.cli run-etl   --load-mode incremental-by-date   --date-column date_posted   --primary-key id
```

#### Incremental by primary key

```bash
python3 -m src.entrypoints.cli run-etl   --load-mode incremental-by-primary-key   --primary-key id
```

#### Incremental by hash

```bash
python3 -m src.entrypoints.cli run-etl   --load-mode incremental-by-hash   --primary-key id   --hash-column row_hash
```

#### Incremental by primary key + hash

```bash
python3 -m src.entrypoints.cli run-etl   --load-mode incremental-by-primary-key-and-hash   --primary-key id   --hash-column row_hash
```

All incremental commands resolve to `versioned` write semantics. Direct `append` is intentionally not exposed for business tables.

### 7. Build AI documents, chunks, and embeddings

```bash
python3 -m src.entrypoints.cli run-ai-indexing
```

Or explicitly choose profile:

```bash
python3 -m src.entrypoints.cli run-ai-indexing   --profile jobs_rag_local
```

This command reads `is_current = true` rows from the main table and refreshes:
- `AI_DOCUMENT_TABLE`
- `AI_CHUNK_TABLE`

### 8. Ask questions over indexed current jobs

```bash
python3 -m src.entrypoints.cli answer-query   --question "Find data engineer jobs in Berlin with Spark"   --top-k 5
```

Or explicitly choose profile:

```bash
python3 -m src.entrypoints.cli answer-query   --profile jobs_rag_local   --question "Find remote Python jobs with AWS"   --top-k 5
```

## Recommended execution order

```bash
python3 -m src.entrypoints.cli run-jobs-ingestion
python3 -m src.entrypoints.cli run-etl --profile full_refresh
python3 -m src.entrypoints.cli run-etl --profile historized_snapshot --primary-key id
python3 -m src.entrypoints.cli run-ai-indexing
python3 -m src.entrypoints.cli answer-query --question "Find Spark jobs in Berlin" --top-k 5
```

## Notes

- `historized_snapshot` is the safest production default for business entities
- `id` is the recommended primary key for jobs; `job_url` can change over time
- `HASH_COLUMNS` should contain only business fields; do not include `date_created`, `date_loaded`, `run_id`, `dt`, `environment`, or `is_current`
- AI indexing should run **after** ETL, not inside the ETL transform or writer layer
- the local AI profile is intentionally provider-agnostic; production providers can be added through the registries without changing orchestration code

## Reset tables if schema changed

```bash
psql -h localhost -U postgres -d world -c "drop table if exists jobs;"
psql -h localhost -U postgres -d world -c "drop table if exists ai_documents;"
psql -h localhost -U postgres -d world -c "drop table if exists ai_chunks;"
python3 -m src.entrypoints.cli run-etl --profile full_refresh
python3 -m src.entrypoints.cli run-ai-indexing
```
