# solid_etl_refactor_template

A refactoring template for a SOLID, profile-driven ETL project.

## What this project does

This project provides a clean separation of ETL concerns:

- ingestion
- normalization
- hash-based change detection
- historized writes into Postgres

The architecture is profile-driven and registry-based. The orchestration layer depends on contracts, not on concrete implementations.

## Architecture principles

- **Single Responsibility**: extractor, transformer, detector, writer all do one job
- **Open/Closed**: new detectors and writers are added through registries
- **Liskov Substitution**: pipelines work with contracts
- **Interface Segregation**: small, focused ETL contracts
- **Dependency Inversion**: use cases depend on registries and interfaces, not on raw SQL

## Data layer

### ETL profiles

- `full_refresh`
  - detector: `full`
  - initial writer: `replace`
  - later chunk writer: `append`
- `historized_snapshot`
  - detector: `incremental-by-primary-key-and-hash`
  - writer: `versioned`

### System column logic

- `date_created` — when the entity first appeared
- `date_loaded` — when the current version was loaded
- `row_hash` — calculated only from business columns in `HASH_COLUMNS`
- `is_current` — current active version of the entity

### Versioned behavior

- new `primary_key` → insert current row
- same `primary_key` + same `row_hash` → do nothing
- same `primary_key` + changed `row_hash`:
  - old row becomes `is_current = false`
  - new row is inserted with `is_current = true`
  - old `date_created` is preserved
  - new `date_loaded` is generated by the pipeline

## Docker (recommended)

This repository ships with a ready-to-use Docker setup under `deploy/`.

### Build the image

From the project root:

```bash
docker compose -f deploy/docker-compose.yml build
```

### Start Postgres (container)

```bash
docker compose -f deploy/docker-compose.yml up -d postgres --wait
```

### Run the CLI inside Docker

Show help:

```bash
docker compose -f deploy/docker-compose.yml run --rm etl \
  python -m src.entrypoints.cli --help
```

Run ingestion (writes a CSV under `data/`):

```bash
docker compose -f deploy/docker-compose.yml run --rm etl \
  python -m src.entrypoints.cli run-jobs-ingestion
```

Run full refresh (first load):

```bash
docker compose -f deploy/docker-compose.yml run --rm etl \
  python -m src.entrypoints.cli run-etl --profile full_refresh
```

Run historized snapshot (incremental/versioned semantics):

```bash
docker compose -f deploy/docker-compose.yml run --rm etl \
  python -m src.entrypoints.cli run-etl --profile historized_snapshot --primary-key id
```

Notes:

- `deploy/docker-compose.yml` starts a Postgres container and builds an `etl` container.
- The `etl` service mounts `./src` and `./data` into the container, so code/data changes are picked up without rebuilding.
- `deploy/.env.example` is loaded by default; you can copy it to `deploy/.env` and adjust values.

## Recommended execution order

```bash
python3 -m src.entrypoints.cli run-jobs-ingestion
python3 -m src.entrypoints.cli run-etl --profile full_refresh
python3 -m src.entrypoints.cli run-etl --profile historized_snapshot --primary-key id
```

## Notes

- `historized_snapshot` is the safest production default for business entities
- `id` is the recommended primary key for jobs; `job_url` can change over time
- `HASH_COLUMNS` should contain only business fields; do not include `date_created`, `date_loaded`, `run_id`, `dt`, `environment`, or `is_current`
- `HASH_COLUMNS` should contain only business fields; do not include `date_created`, `date_loaded`, `run_id`, `dt`, `environment`, or `is_current`

## Python SDK (dlt-like style)

You can now use a decorator-based Python API without FastAPI. The SDK keeps the
existing chunking and historized/versioned writer logic because it still builds
and runs the same core `Pipeline` internally.

```python
from src import pipeline, resource, source

@resource(
    name="player",
    table_name="player",
    primary_key="id",
    columns=["username", "country", "followers"],
)
def chess_players(players: list[str]):
    for idx, player in enumerate(players, start=1):
        yield {
            "id": idx,
            "username": player,
            "country": "unknown",
            "followers": 0,
        }

@source(name="chess")
def chess_source(players: list[str]):
    return [chess_players(players)]

p = pipeline(
    pipeline_name="chess_pipeline",
    destination="postgres",
    dataset_name="player_data",
    credentials={
        "host": "localhost",
        "port": 5432,
        "database": "world",
        "user": "postgres",
        "password": "postgres",
    },
    profile="historized_snapshot",
    primary_key="id",
    hash_columns=["username", "country", "followers"],
    extract_chunk_size=1000,
    write_chunk_size=500,
)

p.run(chess_source(players=["magnuscarlsen", "rpragchess"]))
```

What stays the same under the hood:

- `extract_chunk_size` still drives chunked extraction
- `write_chunk_size` still controls chunked loading into Postgres
- `historized_snapshot` still uses the existing versioned writer
- `row_hash`, `date_created`, `date_loaded`, `is_current` are still generated by the same runtime logic

See `examples/decorator_pipeline.py` for a runnable template.
